## 1. 動作環境の制約（研究機関・閉域環境向け）

* Python 3.10 以上。Linux（Ubuntu 22.04/24.04）と Windows 11 の両方で動くこと。
* ランタイムで外部ネットワークに一切アクセスしない。 CDN、テレメトリ、自動ダウンロード、外部 API は禁止。
* Web ビューアの JS ライブラリ（Three.js 等）は CDN ではなく `static/vendor/` に同梱する。
* `pip install` のみで導入可能（`sudo`・conda 不要）。`requirements.lock` でバージョンを固定し、 オフライン導入用に `scripts/build_wheelhouse.sh`（`pip download` で wheel を集める）を用意する。
* 依存ライブラリは MIT / BSD / Apache-2.0 など寛容なライセンスのみ。GPL 系は必須依存にしない。 `pip-licenses` でライセンス一覧（`LICENSES.md`）を生成するスクリプトを用意する。
* GPU 不要。CPU のみで実用速度が出ること。GPU や OpenGL は任意のオプション扱い。
* サーバのデフォルトは `127.0.0.1` バインド。外部公開する場合は設定でトークン認証を有効化できること。
* `pickle` で外部データを読み込まない。設定は YAML + pydantic で検証する。
* Docker は任意（`Dockerfile` は用意するが、Docker なしで動くことを前提とする）。

### 推奨依存（理由付きで最終判断してよい）

* 必須: `numpy`, `scipy`, `pydantic>=2`, `fastapi`, `uvicorn`, `pyyaml`, `pillow`, `open3d`（Embree による CPU レイキャスト）
* 高速化: `numba`（任意。なくても動くフォールバックを用意）
* 任意: `spiceypy`（高精度な太陽位置。カーネルは手動配置）、`tifffile`（実 DEM 読み込み）
* テスト: `pytest`, `hypothesis`（任意）

## 2. アーキテクチャ

```
lunarsim/
  core/          # 物理・幾何。FastAPI に依存しない純粋ライブラリ
    frames.py        座標系・変換（右手系、ローカル ENU、単位は SI）
    terrain/         地形生成（基盤地形、クレーター、岩石、実 DEM 読み込み）
    illumination/    太陽位置、影、反射モデル、ライト
    sensors/         camera, lidar, imu(任意)
    rover/           運動学モデル、地形への接地
    world.py         World = 地形 + 太陽 + ローバー + センサ群
    sim.py           時間ステップ、決定論的な実行ループ
  api/           # FastAPI の薄いラッパ（ロジックは core に置く）
  viewer/        # ブラウザビューア（Three.js 同梱）
  io/            # PLY/PCD/PNG/EXR、KITTI/TUM 形式の軌跡出力
configs/         # YAML のシナリオ例
scripts/         # デモ、データセット生成、wheelhouse 作成
tests/
```

原則:

* `core` は FastAPI なしで import・利用できること（Jupyter やバッチ処理から直接使える）。
* すべての状態は `World` オブジェクトに集約し、`seed` と設定 YAML から完全に再構築できること。
* 座標系: ワールドはローカル ENU（x=東, y=北, z=上）、ローバー機体系は x 前・y 左・z 上、 カメラは OpenCV 規約（x 右・y 下・z 前）。変換は `frames.py` に集約し、`CLAUDE.md` に図示する。
* 単位はすべて SI（m, s, rad, W/m²）。API の入出力で度を使う場合は名前に `_deg` を付ける。

## 3. 地形生成

### 3.1 基盤地形

* 高さマップ（規則格子 DEM）。解像度・範囲は設定可能（例: 0.05〜0.5 m/px、200 m〜2 km 四方）。
* 自己アフィンなフラクタル地形をスペクトル合成（パワースペクトル ∝ k^-β）で生成。 RMS 斜度、Hurst 指数、大域的な傾斜（南極域の斜面を想定）をパラメータ化する。
* 実 DEM（LOLA 等の GeoTIFF）を読み込み、その上に小スケールのフラクタル細部とクレーターを重ねるモードを用意する（`tifffile` は任意依存）。

### 3.2 確率分布によるクレーター

* サイズ頻度分布（SFD）: 累積分布 N(>D) = c · D^(-b) のべき乗則を基本とし、 `D_min`, `D_max`, 係数 `c`（面密度）、指数 `b` を設定可能にする。 デフォルトは小クレーターの平衡分布（b ≈ 2）付近とし、生成分布（より急な指数）も選べるようにする。 参考文献（Trask 1966 の平衡分布、Neukum production function 等）を確認したうえで値と出典をコメントに書くこと。
* 直径は逆変換法でサンプリング、位置は一様ポアソン点過程（オプションで二次クレーターのクラスタリング）。
* 形状モデル（単純クレーター）: 放物面のボウル + 縁の盛り上がり + 噴出物ブランケット。
  * 深さ/直径比 d/D: 新鮮 ≈ 0.2 → 劣化で ≈ 0.05 程度まで。劣化度を確率的に割り当てる。
  * 縁の高さ ≈ 0.04 D 程度（文献で確認）。
  * 噴出物厚さは距離の −3 乗程度で減衰（McGetchin et al. 1973 を参照）。
  * 劣化はガウシアン拡散（地形拡散）で表現してもよい。
* 重なり順（古いクレーターに新しいクレーターが上書き）を年代順で処理する。
* 各クレーターのメタデータ（中心、直径、深さ、劣化度）を ground truth として出力する。

### 3.3 岩石

* 岩石の大きさ分布は累積面積率モデル（Golombek & Rapp 1997 の指数モデル）を参照。
* 岩石はハイトマップに加算するか、別メッシュとしてレイキャスト対象に含める（計画時に選択肢を提示）。
* クレーター縁・噴出物域で岩石密度を上げるオプション。

### 3.4 出力

* ハイトマップ、法線、斜度マップ、セマンティックラベル（平地／クレーター内壁／縁／岩／影）。
* レイキャスト用の三角形メッシュ（タイル分割と LOD を考慮。範囲が広いときのメモリ使用量に注意）。

## 4. 太陽・照明

### 4.1 太陽位置

* 2 つのモードを用意する:
  1. 手動モード: 太陽方位角・仰角を直接指定（テストと再現性のため）。
  2. 天文モード: 月面の緯度経度と UTC 時刻から太陽方向を計算。 簡易解析モデル（朔望月 29.53 日、月の自転軸傾斜 約 1.54° 等）をデフォルトにし、 `spiceypy` とローカルに置いた SPICE カーネルがあれば高精度モードに切り替える。
* 月の南極域（太陽仰角が数度以下で長い影ができる環境）を代表シナリオとして必ず含める。
* 地球の方向も計算し、地球照（earthshine）を弱い第二光源として任意で加える。

### 4.2 影

* 太陽方向へのシャドウレイ（Open3D の RaycastingScene）で地形自身の落とす影を計算する。
* 太陽の視直径（約 0.53°）を考慮した半影（ソフトシャドウ）をサンプリングで任意実装。
* 静的な太陽方向では、高さマップのホライズンマップをキャッシュして高速化する方法も検討する。
* 永久影（PSR）に近い領域を時間積分で可視化するユーティリティ（任意、後半の Phase で）。

### 4.3 反射モデル（レゴリス）

* 月面特有の反射を表現するため、Lambert ではなく Lunar-Lambert（McEwen）または Hapke モデルを実装する。 衝効果（opposition surge）を含めること。パラメータは設定可能にし、デフォルト値は文献（例: LROC 関連の Hapke パラメータ推定論文）から出典付きで設定する。
* 大気がないので環境光はゼロ（地球照と、任意で地形からの一次相互反射のみ）。

### 4.4 ローバーのライト

* スポットライト（位置、向き、配光角、減衰角、光束）を複数設定可能にする。
* 逆二乗減衰、配光プロファイル、ライトからのシャドウレイによる影を実装する。
* 太陽光とライトの寄与を物理単位（放射照度）で合算し、カメラ露出に渡す。

## 5. センサ

### 5.1 カメラ

* ピンホールモデル + Brown-Conrady 歪み。内部パラメータ・解像度・視野角は設定可能。
* レンダリング方式: Open3D RaycastingScene で各画素の交点・法線・距離を取得し、 numpy（または numba）で照明計算とシャドウレイを行う CPU レイキャスト方式をデフォルトにする。
* センサモデル: 露出時間、ゲイン、ショットノイズ、読み出しノイズ、暗電流、飽和、量子化（8/12/16 bit）。 月面は明暗差が極端なので、白飛び・黒つぶれが再現されること。自動露出は任意。
* 出力: 画像（PNG / 16bit）、深度、法線、セマンティックラベル、カメラ姿勢（ground truth）。
* ステレオカメラ（基線長を設定可能）に対応する。

### 5.2 LiDAR

* スキャンパターンを差し替え可能にする:
  * 回転式マルチビーム（例: 16/32/64 ライン、垂直角テーブルを設定で指定）
  * 非繰り返しパターン（ロゼット型。Livox 系を想定）
  * 固定 FOV のフラッシュ型
* 誤差モデル: 測距ガウスノイズ（距離依存）、入射角と反射率に応じた検出確率（欠測）、 最大／最小レンジ、ビーム広がり（複数サブレイの平均、任意）、強度値の出力。
* 走行中のスキャンによるモーション歪み（任意）。
* 出力: 点群（N×4: x, y, z, intensity）、ring/time フィールド、PLY/PCD 書き出し、ground truth の姿勢。

### 5.3 IMU（任意・後半 Phase）

* 月重力 1.62 m/s²、バイアスとランダムウォークを持つ 6 軸 IMU。

## 6. ローバー

* 運動学モデル: スキッドステア（差動駆動）と Ackermann を切り替え可能にする。
* 地形への接地: 車輪接地点の高さから姿勢（ロール・ピッチ）とボディ高さを求める（剛体の静的接地でよい）。
* 斜度に応じたすべり率の簡易モデル（パラメータ化。テラメカニクスの詳細実装は範囲外）。
* 最大斜度・転倒判定の警告を出す。
* センサの取り付け位置・姿勢（extrinsics）を YAML で定義する。
* 特定の実機の非公開仕様は含めない。寸法・センサ構成は汎用的なサンプル値で、すべて設定可能にする。

## 7. FastAPI サーバ

### REST（例。最終設計は計画時に提案）

* `POST /worlds` … 設定（YAML/JSON）とシードから World を生成し `world_id` を返す
* `GET /worlds/{id}` … メタデータ（範囲、解像度、クレーター数、太陽状態）
* `GET /worlds/{id}/heightmap` … 高さマップ（npy / 16bit PNG）
* `GET /worlds/{id}/craters` … クレーター一覧（ground truth）
* `PUT /worlds/{id}/sun` … 太陽を手動指定、または時刻・緯度経度で更新
* `POST /worlds/{id}/rover/cmd` … 速度指令（v, ω）またはウェイポイント
* `POST /worlds/{id}/step` … 指定時間だけ進める（決定論的）
* `GET /worlds/{id}/sensors/camera/{name}` … 画像（+ 任意で深度・ラベル）
* `GET /worlds/{id}/sensors/lidar/{name}` … 点群（バイナリ形式を推奨、JSON は小規模時のみ）
* `GET /health`, `GET /version`

### WebSocket

* `/ws/{world_id}` … ローバー姿勢・センサデータのストリーミング、指令の受信。

### 要件

* OpenAPI ドキュメントが自動生成されること（`/docs`）。
* 重い処理（レンダリング・点群生成）はイベントループをブロックしないようにする（スレッドプール等）。
* Python クライアント（`lunarsim.client`）を用意し、REST/WebSocket を簡単に呼べるようにする。
* ROS 2 ブリッジは将来拡張として、インターフェースだけ考慮しておく（今回は実装しない）。

## 8. ビューア

* ブラウザで地形（ハイトマップから生成したメッシュ）、太陽方向、影、ローバー、LiDAR 点群、カメラ画像を表示する。
* 太陽の方位角・仰角のスライダー、ライトの ON/OFF、キーボードによるローバー操縦。
* JS ライブラリはすべて同梱（オフラインで動作すること）。

## 9. データセット出力

* シナリオ YAML とシードからバッチでデータセットを生成するスクリプト。
* 出力形式: 画像列、点群列、ground truth 軌跡（KITTI 形式と TUM 形式）、カメラ・LiDAR のキャリブレーションファイル。
* SLAM や Visual Odometry の評価にそのまま使えること（例: 同じ経路を太陽仰角だけ変えて複数回出力）。

## 10. テストと検証

* `pytest` で以下を必ずテストする:
  * クレーター SFD: サンプリング結果が指定のべき乗則に従うこと（KS 検定など統計的に確認）
  * 再現性: 同じシード・設定で、地形・画像・点群がビット単位で一致すること
  * 太陽位置: 手動モードの方向ベクトル、簡易天文モードの周期性
  * 影: 既知の幾何（平面上の箱など）で影の長さが解析解と一致すること
  * LiDAR: 平面ターゲットに対する測距誤差の統計がノイズ設定と一致すること
  * カメラ: 投影・逆投影の往復誤差、歪みモデル
  * 座標変換: 往復変換の誤差
* 性能目標（ノート PC の CPU で計測し、README に結果を記載）:
  * 1 km² / 0.25 m 解像度の地形生成: 数十秒以内
  * 640×480 カメラ画像（影あり）: 1 秒以内を目標
  * 32 ライン LiDAR 1 スキャン: 0.2 秒以内を目標
  * 目標に届かない場合はボトルネックを計測して報告し、改善案を提示すること。
* ruff + mypy（strict は core のみでよい）、型ヒント必須、docstring は物理量の単位を明記する。

## 11. Phase 分割（目安）

## 12. やってはいけないこと

* ランタイムでのネットワークアクセス、CDN 読み込み、テレメトリ
* 根拠のない物理パラメータを断定的に書くこと（出典を書くか、TODO と設定可能化で対応）
* FastAPI 層への物理ロジックの混入
* シードを経由しない乱数の使用（`np.random` のグローバル状態を使わず `Generator` を渡す）
* 特定の実機・プロジェクトの非公開情報を想定した値の埋め込み
